# AGENTS.md

This file provides guidance to Codex (Codex.ai/code) when working with code in this repository.

## What this repo is

This is **not** primarily a design system — it is a falsifiable architectural claim about contract-governed compositional systems, with a Web DOM design system as the existence proof. One polymorphic primitive (`Stack`) plus JSON contracts drive code generation for the **five Web DOM** framework targets (React, Vue, Svelte, Angular, Lit), plus React Native, a Figma descriptor target, and the explicit-only native targets (SwiftUI, Jetpack Compose). If the same contract can drive all of them idiomatically without leaking framework details, the contract is at the right level of abstraction.

The registered target set is authoritative in `fsds.targets.json` (nine builtin targets today); the **rail-admitted** subset is authoritative in `packages/ds-codegen/src/validation/admission-descriptor.ts` (six: the five web frameworks plus react-native). Never hand-count either from prose.

Read `docs/current-implementation-snapshot.md` first to know what is currently proven vs. only foundation. That document overrides older architecture docs when they disagree.

1. `docs/current-implementation-snapshot.md` (claim ledger)

### Pre-push hook tracks CI, but is change-scoped — CI is authoritative

`.githooks/pre-push` runs the same gate families as `.github/workflows/ci.yml` — install, lint, typecheck, the token gates, `generate:check`, `docs:check-claims`, tests, `governed:rail`, the iconography ledger, and the six derived-obligation audits. Activate per-clone with `git config core.hooksPath .githooks` (the `prepare` script attempts this automatically).

It is **not** a step-for-step mirror. `scripts/prepush-scope.mjs` derives a per-push flag set from the changed paths and the hook skips families whose inputs did not change (`PREPUSH_FULL=1` forces the full sequence). The hook's own header states it "can over-skip relative to CI but never silently skips a step whose input changed; CI is authoritative." So a green pre-push means *the lanes your change touched* passed — it is not a proof that CI will pass. Do not `--no-verify` to dodge gate failures — fix the underlying issue.

### CAWS slice lifecycle (spec → worktree → work → merge → evidence → close)

Non-trivial work is governed by a CAWS spec so its provenance is recorded. The full flow, in order:

1. **Create the spec before any work.** `caws specs create <SPEC-ID> --title "…" --mode feature --risk-tier 2 --scope-in <paths…> --acceptance "given…; when…; then…" --contract <name>:<type>[:<path>]`. Fill `invariants:` + `blast_radius:` in the YAML, validate with `caws specs validate <file>`; the CLI commits the spec itself. Tier 1/2 specs require at least one `contract:` entry.
2. **Create a bound worktree — never a plain branch.** `caws worktree create <name> --spec <SPEC-ID> --base-branch main`, then do ALL work under `.caws/worktrees/<name>/`. The binding enforces `scope.in`; gitignored dependency artifacts (`node_modules`, `.pnpm-store`) are symlinked in, but gitignored build outputs are not — rebuild `packages/ds-tokens/generated/composed.tokens.json` (and friends) inside the worktree before running gates. Scoped commits (`feat(…)`, `fix(…)`, `docs(…)`, one per logical phase). When done, run the full gate locally inside the worktree: `pnpm run governed:rail && pnpm test && pnpm run test:frameworks`. Plain `git checkout -b` branches bypass the binding/scope enforcement — this is a correctness requirement for concurrent agents, not a style preference.
3. **Merge via the caws CLI with `--no-close`.** From the canonical checkout, first verify `git branch --show-current` is `main` (lifecycle commits land on the current HEAD — see the concurrency rule below). Then `caws worktree merge <name> --dry-run`, then `caws worktree merge <name> --no-close`. Do NOT rely on the default auto-close: its close commit is committed at the canonical checkout's current HEAD, which under concurrent sessions may not be `main` (incident 2026-08-14, `RAIL-COMPONENT-CONTRAST-01`: the merge landed on `main` but the auto-close commit landed on another session's feature branch and had to be cherry-picked back). **`origin` still only ever receives `main`** — never push a feature branch. The pre-push hook fires only on `git push`, so a local merge never skips the gate — the *next* `git push origin main` runs it over the merged range.
4. **Record acceptance-criteria evidence while the spec is still ACTIVE.** For each `A1…An`: `caws specs evidence <SPEC-ID> --ac A1 --status pass --evidence-ref "<command or test proving the criterion>"` (or `--status waived --waiver-reason "…"`). Evidence is REFUSED once the spec is closed — this is exactly why step 3 uses `--no-close` (the lesson from `ICONOGRAPHY-EMISSION-LEDGER-01`, re-learned by `RAIL-COMPONENT-CONTRAST-01`).
5. **Close after the merge is on `main` and the evidence is in.** `caws specs close <SPEC-ID> --resolution completed --merge-commit <merge-sha> --reason "<one-line summary>"`. Keep `--reason` a **single line** — a multi-line block-scalar trips a known `partial_failure_unrecovered` defect in the close path. `caws specs close` auto-commits the YAML flip as its own `chore(caws): close <SPEC-ID>` commit, so the working tree stays clean.

**Concurrency rule — the canonical checkout's HEAD is shared state.** Every caws lifecycle commit (spec create/bind/evidence/close) commits at whatever branch the canonical checkout has checked out. Keep the canonical checkout on `main`, and never switch branches there while another session's slice is mid-flight — work belongs in worktrees precisely so agents don't clobber each other. If you find the canonical checkout on a branch you didn't set, another session is working; coordinate (or `caws aim`) before touching HEAD.

**Do not** hand-edit `.caws/specs/*` lifecycle fields, `.caws/events.jsonl`, or `.caws/worktrees.json` — use the CLI. **Do not** `caws specs close` *before* merging and then also run `caws worktree merge` — the double-close is mutually exclusive and fails; the one path is the flow above (`--no-close` merge → evidence → manual close). Never weaken a guard to get past it.

### CAWS runtime hooks govern every session (`.Codex/hooks/`)

Separate from the git pre-push hook above, this repo installs the **CAWS Codex hook pack** under `.Codex/hooks/`. These fire on `PreToolUse` / `PostToolUse` / `SessionStart` / `Stop` / `PreCompact` (wired in `.Codex/hooks.json` → `codex/hooks/caws_dispatch/`) and actively gate your work — some **block** tool calls. The ones most likely to stop you:

- **block-dangerous.sh** (`Bash`) — denies catastrophic commands and arms a sticky per-session **danger latch** on `ask:confirm`; once latched, all mutating commands block until the user runs `reset-danger-latch.sh`.
- **scope-guard.sh** (`Write`/`Edit`) — out-of-scope edits escalate by **strike** (advise → ask → block); fix with `caws specs amend-scope`, clear stale strikes with `reset-strikes.sh`.
- **worktree-guard.sh** / **worktree-write-guard.sh** / **bash-write-guard.sh** — block history-rewriting git and cross-worktree / claimed-path writes via the shared claim oracle.
- **protected-paths.sh** — hard-blocks `Write`/`Edit` under `.Codex/hooks/*` and to strike-state files.

**Full reference (every active hook, the dormant ones, escape hatches, state-file locations): [`.Codex/hooks/README.md`](.Codex/hooks/README.md).** Hook scripts are CAWS-managed (`do_not_edit_directly`) — change them via `caws init`, never by editing in place, and never weaken a guard to get past it.

## Architecture

### Layer authority (read `docs/codegen-authority.md` before touching emitters)

```
Contract              declares component semantics
Semantic IR           normalizes contract into framework-neutral facts
Framework emitter     lowers IR into idiomatic framework syntax
Admission rail        validates emitted artifacts pass framework tooling
Behavioral tests      validate runtime behavior satisfies the contract
```

The central architectural invariant: **a component's durable semantics live in the contract, with each framework as a realization backend.** Emitters must not accumulate hand-authored per-component lore (`if (component === "ShowMore") …`). If you find yourself special-casing a component name in an emitter, the IR is missing a fact — push the fact down into the IR, not up into the emitter.

- Contract knows: "this part is a trigger," "this channel is `open`," "role `option`."
- IR knows: "text-node child binding," "ARIA Booleanish attribute," "host has implicit role."
- Emitter knows: "in Svelte, text children are `{expr}` not `textContent={expr}`."
- Rail knows: "the Svelte compiler rejects this." It does **not** decide "therefore X is special."

### Source-of-truth corpus

Component contracts live at `packages/ds-contracts/components/<Name>/<Name>.contract.json` with optional sidecars:

- `<Name>.tokens.json` — token bindings
- `<Name>.styles.json` — style declarations
- `<Name>.usage.jsonl` — curated documentation examples (rendered in the Design view; **not** codegen input)

The filesystem loader (`packages/ds-codegen/src/contracts-fs.ts`) is authoritative for corpus discovery — never trust hand-written component counts in prose/docs.

The single *rendered* primitive contract is `packages/ds-contracts/primitives/Stack.primitive.json` — the only primitive that emits component source (via `emitPrimitives`). Per-target import paths are declared in `implementation.targets.<framework>.relativeFromComponents`.

`primitives/` also holds `BoxModel.primitive.json`, which is **not** a rendered primitive: it validates against `packages/ds-contracts/box-model.primitive.schema.json` (not `primitives/primitive.contract.schema.json`), its keys are `box-model.*` geometry slots, and it emits nothing. It is the canonical defaults table read by `loadBoxModelPrimitive` in `packages/ds-codegen/src/box-model.ts`. "One primitive" in the thesis docs means one rendered primitive, and remains accurate.

### Behavior primitives are mirrored across frameworks

Each **web** framework package ships the same primitive set under different names (`useFocusTrap` / `createFocusTrap` / `FocusTrapController`). The API contract is identical — same options shape, same channel keys — so codegen dispatches from IR to target-specific implementations. If you add a behavior primitive, add it to all five web packages.

React Native carries only the subset that has a native meaning — today `createCompoundContext` beside `stack.tsx`. The DOM-bound primitives (`useFocusTrap`, `usePortal`, `useScrollLock`, `useDismissal`, `useAnchorToggle`, `useFieldAssociation`, …) have no RN counterpart by design, so "add it to all five" is a web-family rule. When a new primitive *does* have a native meaning, port it to `packages/ds-react-native/src/primitives/` too — check, don't assume.

### Generated artifact admission rail

The rail binds emitted bytes to four evidence rungs: artifact, contract, codegen-source, environment. `pnpm run governed:rail` regenerates everything and then verifies in required mode; the verifier emits typed `RAIL_*` diagnostic codes when integrity claims drift. CI also runs `git diff --exit-code` over the **six** generated `src/` trees after the rail (the five web packages plus `packages/ds-react-native/src`) — proves the regenerated bytes were already committed.

The emission manifest at `packages/ds-codegen/.emission-manifest.json` is **gitignored** runtime state. It is "what the last `generate` run produced on this machine." Schema migrations are regenerate-driven (no data migration) — a stale manifest triggers `RAIL_REQUIRE_MANIFEST_SCHEMA_MISMATCH`, repair is `pnpm run generate -- --target=all`.

Read `docs/specifications/admission-rail.md`, `docs/specifications/governed-ci.md`, `docs/specifications/manifest-schema.md` before touching anything under `packages/ds-codegen/src/validation/`.

### Token graph

`composed.tokens.json` is gitignored regenerable scratch; `resolved.tokens.json` and `tokens.css` are COMMITTED outputs, drift-gated by `tokens:build:check` (the contrast validators — curated and component-derived — read `resolved.tokens.json`). Every CI/pre-push run still starts with `pnpm -F @full-stack-ds/tokens build` before running `generate:check`, because the semantic check loads the composed graph to verify contract `resolvesTo` paths. Without that build, every contract reports `token graph not built` DRIFT.

Brand override files do **not** participate in the main token build's ref validation (they layer separately). `tokens:check-brand-refs` is the gate that catches unresolved `{ref}`s in brand overrides — without it, a typo like `{color.palette.cobalt.500}` silently no-ops at runtime.

## Common editing workflows

### Editing an existing component

1. Edit `packages/ds-contracts/components/<Name>/<Name>.contract.json` and any sidecars.
2. `pnpm run generate:check` (and `generate:validate-usage` if you changed usage).
3. `pnpm run generate -- --target=all <Name>`.
4. `pnpm test && pnpm run test:frameworks && pnpm run governed:rail`.

**Do not hand-edit generated component files** unless the edit is inside an admitted `@custom:start` / `@custom:end` block (see `packages/ds-codegen/src/preserve.ts`). CSS and pure scaffolding are regenerated and will be overwritten. `--force` exists as an emergency override; using it is a signal that the contract should have carried the change instead.

### Adding a new component

1. Create `packages/ds-contracts/components/<Name>/<Name>.contract.json` against `component.contract.schema.json`.
2. Add sidecars only when needed.
3. `pnpm run generate:check` and `pnpm run generate -- --target=all <Name>`.
4. Add to showcase navigation only if it should appear in the app.

### Schema / IR / emitter changes

If you add or rename a contract field:
1. Update the schema under `packages/ds-contracts/`.
2. Update `packages/ds-codegen/src/ir.ts` so the field has a governed IR representation.
3. Update each affected emitter under `packages/ds-codegen/src/frameworks/<target>/`.
4. Regenerate all and run `pnpm run governed:rail`.

Emitters must not re-parse raw contract fields when the IR should own the translation.

### Adding a new framework target

Built-in targets are admitted via `packages/ds-codegen/src/target-packs/builtin.ts` and need a per-framework admission plan in `packages/ds-codegen/src/validation/frameworks/<target>.ts`. Local target packs declared in `fsds.targets.json` are currently **metadata-only** — their emitter entrypoints are not loaded/executed yet. See `docs/architecture/design/target-pack-registry.md`.

## Non-claims to respect

When reasoning or writing docs/comments, do not over-claim:

- The rail proves **artifact↔contract↔codegen↔env binding**, not determinism, not visual quality, not a11y adequacy, not full environment attestation.
- The runtime fact rail (Playwright, `e2e/runtime-rail.spec.ts`) proves narrow facts — default and non-default CSS-var fallbacks, and iteration DOM shape — for Progress/Truncate/ShowMore/OTP/Calendar/Shuttle/Walkthrough/Select across **all five** web frameworks including Angular. The one Angular exclusion is the Select callback-capture interaction test, which is skipped because `angular-preview` uses a synthesized-host pipeline rather than the shared `config-entry.ts` callback bus — not because Angular preview is unproven. It does not prove cross-framework behavioral parity beyond DOM shape, or visual quality. Screenshot baselines are darwin-only and skip under `CI=true` — CI runs OS-agnostic fact assertions.
- React Native is a **rail-admitted default target**: it is in `admission-descriptor.ts`, `--target=all` and `governed:rail` emit and verify it, and CI's generated-tree diff covers `packages/ds-react-native/src`. It is not recon. SwiftUI and Jetpack Compose *are* explicit-only builtin targets outside rail verification and outside CI drift diffs — SwiftUI emits the full 49-component corpus and Compose emits two components, both compiled by dedicated CI native lanes over hand-authored example consumers, which proves compilation, not component correctness.
- Web DOM is the only family proven end-to-end (emit → rail → runtime). It is **not** the only admitted executable family.
- `@full-stack-ds/*` packages are **workspace-only**; not published to npm.
- Local target packs are metadata-only (`LOCAL_TARGET_PACK_EXECUTION_STATUS` in `target-packs/local.ts`) until an executable local-loader slice lands. Note `fsds.targets.json` currently declares **no** local packs — all nine registered targets are `kind: "builtin"`.
- The two native compile lanes (Kotlin/`kotlinc`, Swift/`swiftc`) compile hand-authored example consumers, not the generated component trees. They prove the rail can drive a non-pnpm toolchain; they do not drift-gate emitted native bytes.
- Figma descriptor emission ≠ live Figma library publication.

## Conventions specific to this repo

- **No shadow files** — no `*-enhanced.*`, `*-v2.*`, `*-new.*`. Edit in place.
- **No `package-lock.json` or `yarn.lock`** — gitignored to keep pnpm authoritative.
- **`pnpm run prepare`** wires `core.hooksPath = .githooks` so the pre-push gate activates on first install.
- **Conventional commits** with scopes that name the area: `feat(figma-plugin): …`, `fix(e2e): …`, `docs(architecture): …`, `wip(<scope>): checkpoint …`.
- Tests that produce visual evidence (screenshots) write under `test-results/` (gitignored) and `tmp/` (gitignored, project scratch).
- When a script touches `composed.tokens.json` or anything under `packages/ds-codegen/.emission-manifest.json`, it is touching gitignored regenerable state — never commit those files.
